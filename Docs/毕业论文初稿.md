面向移动端的轻量级全局光照焙系统设计与实现
摘要：全局光照是实时渲染中提升画面真实感的核心技术之一。但在移动端及中低端硬件平台上，算力与显存带宽的双重瓶颈使多数高质量 GI 方案难以直接落地——它们要么依赖密集的像素级纹理采样，要么需要额外的渲染通道和大体积缓存。针对这一矛盾，离线烘焙路线将高成本的光线追踪计算前置到离线阶段，运行时只承担低复杂度的信号重建，理论上很适合资源受限场景。然而从学术原型到可运行的工程系统之间仍有不小的距离：离线拟合与运行时着色器的数值一致性、跨工具链的数据格式对齐、以及面向具体引擎的集成方案，都是实际开发中绕不开的难题。

本文以球谐函数（Spherical Harmonics, SH）为理论工具，以 Unity 通用渲染管线（URP）为目标平台，设计并实现了一套端到端的轻量级静态全局光照烘焙系统。系统打通了从场景网格导出、离线预计算到运行时着色重建的完整数据闭环，并在 128 探针、二阶 SH 的配置下完成了全链路验证。本文的主要工作和创新点如下：

（1）构建了参数化、可复现的离线烘焙管线。离线端依次执行表面蓝噪声采样、基于 BVH 加速的防漏光路径追踪、K-Medoids 探针空间聚类以及带 L2 正则化的加权岭回归 SH 求解，最终将各探针的球谐系数打包为结构紧凑的一维 RGBAHalf 条带纹理。整条管线通过固定随机种子和命令行参数化脚本保证任意机器上的可复现性。

（2）提出了一种基于顶点着色的极低开销运行时重建方案。在 Unity URP 的基础渲染通道中，利用网格次级纹理坐标（UV2）编码每个顶点到最近两个探针的索引与逆距离权重，在顶点着色器内完成双探针系数混合与 SH 基函数求值，将间接光照的计算负载从片元级降至顶点级，从而避开了移动端 GPU 最敏感的像素级纹理寻址开销。

（3）建立了一套面向工程鲁棒性的校验与容错机制。针对实际开发中暴露的关键缺陷进行了系统性修复，包括对齐 Python 离线端与 HLSL 运行时端的 SH 卷积常数以消除系统性偏色、在正规方程接近奇异时自动回退至 SVD 伪逆求解以防止流程中断、以及对探针数量与 top-k 等参数实行边界钳制与预警。这些措施使管线在非标输入下仍能保持可执行状态。

（4）在 128 探针、256 半球方向、1024 采样点的主力配置下完成了端到端实跑验证与性能测量。实验结果表明，离线各阶段产物维度一致且无 NaN/Inf 异常；运行时纯 GPU 渲染净开销仅为 0.084 ms，ProbeMap 纹理仅占约 14 KB 显存，相比传统 lightmap 方案有数量级优势，同时能够自然呈现色彩溢出与柔和遮蔽等 GI 特征。

关键词：静态全局光照；球谐函数；探针烘焙；Unity URP；离线拟合


Design and Implementation of a Lightweight Global Illumination Baking System for Mobile Games
Abstract: Global illumination (GI) is a fundamental technique for enhancing visual realism in real-time rendering. However, on mobile and low-to-mid-range hardware platforms, the dual constraints of limited compute throughput and memory bandwidth render most high-quality GI solutions impractical — they either rely heavily on per-pixel texture sampling or demand additional render passes and large-volume caches. Offline baking offers a theoretically appealing alternative by shifting expensive ray-tracing computations to a precomputation stage, leaving only lightweight signal reconstruction at runtime. Yet the gap between an academic prototype and a robust engineering system remains substantial: numerical consistency between offline fitting and runtime shaders, data format alignment across heterogeneous toolchains, and engine-specific integration are all non-trivial challenges that must be addressed in practice.

This thesis takes spherical harmonics (SH) as its theoretical foundation and Unity's Universal Render Pipeline (URP) as the target platform, and presents a complete end-to-end lightweight static GI baking system. The system establishes a closed data loop spanning scene mesh export, offline precomputation, and runtime shader-based reconstruction, and has been validated end-to-end under a configuration of 128 probes and second-order SH. The main contributions and innovations are as follows:

(1) A parameterized, reproducible offline baking pipeline is constructed. The offline stage sequentially performs surface blue-noise sampling, BVH-accelerated path tracing with light-leakage prevention, K-Medoids probe clustering in the spatial domain, and weighted ridge regression with L2 regularization to solve per-probe SH coefficients. The resulting coefficients are packed into a compact one-dimensional RGBAHalf strip texture. The entire pipeline is made deterministic and reproducible across machines via fixed random seeds and command-line parameterization.

(2) An extremely low-overhead runtime reconstruction scheme based on vertex shading is proposed. Within Unity URP's base render pass, the system encodes each mesh vertex's indices and inverse-distance weights to its two nearest probes into the secondary texture coordinate channel (UV2). Dual-probe coefficient blending and SH basis evaluation are performed entirely in the vertex shader, shifting the indirect lighting computation from the per-pixel level to the per-vertex level. This design circumvents pixel-level texture addressing — the most critical bottleneck for mobile GPUs.

(3) A suite of engineering robustness safeguards is established. Systematic fixes address several critical defects discovered during development: SH convolution constants are aligned between the Python offline code and the HLSL runtime code to eliminate systematic color shifts; the solver automatically falls back to SVD-based pseudo-inversion when the normal equations become near-singular, preventing pipeline crashes; and boundary clamping with warnings is applied to parameters such as probe count and top-k values. These measures ensure the pipeline remains executable even under non-standard inputs.

(4) End-to-end validation and performance measurement are carried out under the primary configuration of 128 probes, 256 hemispherical directions, and 1024 surface samples. Experimental results confirm dimensional consistency and the absence of NaN/Inf anomalies across all offline stages. At runtime, the net GPU rendering overhead is merely 0.084 ms, and the ProbeMap texture occupies only ~14 KB of GPU memory — an order-of-magnitude improvement over conventional lightmap approaches — while naturally reproducing GI features such as color bleeding and soft ambient occlusion.

Key words: Static Global Illumination; Spherical Harmonics; Probe Baking; Unity URP; Offline Fitting

1 绪论
1.1 研究背景与意义
全局光照（Global Illumination, GI）通过统一计算直接光照与间接光照，能够显著增强三维场景的真实感、空间层次感及材质的物理一致性。在实时渲染应用中，全局光照不仅能提供更准确的明暗对比，更能通过光能在几何表面间的多次物理反弹，自然地呈现出色溢（Color Bleeding）、柔和光照遮蔽等复杂的视觉现象。然而，受限于移动终端及中低端设备的算力与显存带宽瓶颈，现有的高质量实时 GI 算法往往难以直接部署：部分方案严重依赖密集的像素级纹理采样，而另一些方案则需引入多重渲染通道（Render Passes）与庞大的缓存数据，极易造成渲染帧耗时过长及内存占用溢出。

针对上述硬件约束，基于离线预计算的静态光照烘焙技术（Offline Baking）展现出了明显优势。其核心思想是将计算代价高昂的光线追踪过程转移至离线阶段，在设备运行时仅执行低复杂度的光照信号重建。尽管这一思路已被广泛应用于工业界，但在前沿算法向实际工程系统转化的过程中，仍存在亟待解决的难点：首先，离线拟合数学模型与运行时着色器实现之间的一致性难以保证，常导致渲染结果严重失真；其次，多维光照数据在跨工具链流转时，缺乏规范的数据封装，极易产生数值灾难；最后，多数理论研究缺乏面向主流三维引擎（如 Unity）的工程化集成方案。

有鉴于此，本文的研究意义在于将先进的球谐光照理论转化为具有高度可落地性的工程实现。本工作致力于在离线端构建一套可参数化、具备强鲁棒性的光照预计算管线；同时深度耦合 Unity 通用渲染管线（URP），打通从离线预计算到运行时着色重建的数据闭环。通过端到端的系统运行与性能验证，本文旨在为资源受限平台提供一套兼具渲染轻量化与工程高可用性的全局光照解决方案，并为类似图形学算法的工程化部署提供参考范式。
1.2 国内外研究现状
在实时渲染领域，静态全局光照方案按其数据表示与运行时查询方式，大致可归为光照贴图（Lightmap）、探针（Probe）以及预计算辐射传输（Precomputed Radiance Transfer, PRT）三大路线。三条路线并非彼此排斥，而是在内存开销、运行时复杂度、视觉质量与工程成本之间各自占据了不同的权衡点。近年来，随着移动端游戏市场的持续扩张，如何在极度受限的硬件预算下交付可接受的 GI 质量，已成为学界与工业界共同关注的焦点。以下分别对三条路线的发展脉络、关键工作及其与本设计的关联进行梳理。
光照贴图是工业界历史最长、部署最广的离线烘焙方案。其基本思想是将经过全局光照计算后的表面出射辐亮度直接写入二维纹理，运行时每个可见片元仅需一次纹理采样即可恢复间接光分量，几乎不增加着色器计算负担。Unity 先后集成了两套光照贴图后端：基于 Enlighten 的 Realtime GI 在离线阶段预计算表面间的可见性关系，运行时根据动态光源实时更新辐亮度，兼顾了静态场景的效率与动态光源的灵活性；而 Progressive Lightmapper 则采用路径追踪的方式逐像素累积光照，支持渐进式的预览迭代，在 Unity 2017 之后的版本中逐渐成为主力烘焙方案。Unreal Engine 同样提供了 GPU Lightmass 作为烘焙加速器，利用 GPU 的大规模并行能力将路径追踪的计算时间压缩至纯 CPU 方案的数分之一，并在 4.22 版本后引入了体积光照贴图（Volumetric Lightmap）来补充表面贴图在体积区域表达的不足。
然而，光照贴图路线的质量上限高度依赖两个前提条件：一是场景必须提供一套无重叠、无拉伸的独立光照贴图 UV（Lightmap UV），这对自动展开算法提出了较高要求——Liu 等人提出的局部/全局网格参数化方法[10]为该问题提供了经典的解决框架，但在复杂的实际生产资产上仍经常需要手动修正接缝与岛间距；二是贴图分辨率必须足够覆盖场景的几何细节，当分辨率受限时，跨表面交界处的辐亮度梯度被强制离散化，容易出现接缝伪影、纹理糊化和块状量化误差。Sloan 与 Silvennoinen 对方向光照贴图的编码策略做了系统性的梳理与改进[4]，指出即便在有限的分辨率下，合理的方向信息封装仍能显著提升法线贴图配合光照贴图时的视觉质量，但这类编码方案本身也会增加纹素占用量。对于移动端而言，一张 1024×1024 的 DXT5/RGBM 压缩光照贴图约占用 1.33 MB 显存，若场景包含多张此类贴图，内存预算将迅速吃紧，这对普遍仅有 2~4 GB 总内存的中低端移动设备构成了实质压力。
综上，光照贴图在运行时性能上占据绝对优势，但其对 UV 展开工艺和贴图分辨率的高要求，使其在移动端大规模场景中面临明显的可扩展性瓶颈。本设计借鉴了光照贴图"离线预计算、运行时低开销"的核心理念，但改用探针作为光照载体，以此避开对全局 UV 展开和密集二维纹理的刚性依赖。
探针路线的核心思路是以空间中的离散采样点阵列表征光场分布，任意空间位置的间接光通过邻近探针的插值获得，从而将光照查询从"查表面纹理"转化为"查空间邻域"。相比光照贴图，探针方案天然不需要场景表面具备一致的 UV 参数化，对任意几何体均能以统一方式查询，因此特别适合包含大量不规则网格或动态物体的场景。
在商业引擎中，Unity 的 Light Probes 是最早广泛部署的探针系统之一。开发者手工或半自动地在场景中放置球谐探针，运行时通过四面体剖分确定查询点落入哪个四面体，再以重心坐标对四个顶点的探针做球谐系数插值，得到该点的环境光照估计。Cupisz[3] 详细阐述了这一插值策略的实现细节与边界处理方案，指出四面体剖分相比简单的最近邻或三线性插值，能在稀疏探针布局下提供更平滑的空间过渡。Unreal Engine 则提供了两个互补的探针体系：Volumetric Lightmaps (VLM)[6] 在场景空间中以规整的三维格网存储每个格点上的低阶球谐系数，查询时对包围查询点的八个格点做三线性插值，其优势在于空间覆盖均匀、实现简单，但存储开销随格网精度成立方增长；Indirect Lighting Cache (ILC)[7] 则采用更稀疏的散点分布，配合空间哈希与自适应密度，以更小的内存代价覆盖大范围场景，但在密度不足的区域可能出现漏光或闪烁。
在商业游戏领域，探针方案已经历了大量实战检验。Iwanicki 与 Sloan 在《使命召唤：无限战争》的技术分享[8]中展示了面向 60 FPS 主机平台的全套预计算探针光照管线，包括探针自动布点、可见性过滤和运行时快速查询等关键环节，其工程深度远超学术原型。在学术前沿，Majercik 等人提出的 Dynamic Diffuse Global Illumination (DDGI)[9] 将探针思路与实时光线追踪相结合：在场景中布置辐照度探针，每帧通过光线追踪动态更新探针中的球谐或八面体映射辐照度，实现了全动态场景下的漫反射 GI，且无需任何离线预计算。DDGI 的出现表明探针框架并不仅限于静态烘焙，其本身是一种灵活的光场采样范式。此外，Kerbl 等人提出的 3D Gaussian Splatting[11] 虽是面向辐射场渲染而非传统 GI 的工作，但其采用的高保真空间点基元表示与探针思路在"以离散基元覆盖连续光场"这一理念上具有可类比之处，反映了该方向在更广泛渲染领域的活跃探索。
不过，探针路线在移动端落地时仍需面对数据组织效率的问题。若每个探针独立存储完整的方向辐照度分布（如采用 64×64 的八面体映射），以 128 个探针计算，仅方向数据即需约 2 MB 显存，采样次数亦随之飙升。因此，如何以紧凑且查询高效的方式表示每个探针的角分布，是探针方案能否在低端设备上实用的关键。本设计选择以二阶球谐（每个探针仅 27 个浮点数）压缩方向信息，借此将探针路线的存储与带宽开销控制在极低水平。
预计算辐射传输（PRT）由 Sloan 等人在 2002 年的 SIGGRAPH 论文[2]中正式提出，其核心思想是将渲染方程中的光照传输函数在球谐基上展开并离线预计算，运行时仅需计算入射光照的球谐系数与预计算传输向量的点积，即可实时获得出射辐亮度。这一框架将场景几何对光的遮挡、反射和散射行为"编码"为一组固定的基函数系数，将原本需要每帧执行的复杂可见性计算转换为低维向量运算。
PRT 的理论基础由 Ramamoorthi 与 Hanrahan[1] 在一年前奠定。他们从球面卷积的角度严格证明了：对于理想的漫反射表面（Lambertian BRDF），其反射的辐照度在频域中是一个仅包含前三阶（L=0,1,2）带宽的极低频信号，对应的 9 个球谐基函数即可覆盖入射光照能量的 99% 以上。这一结论意味着，漫反射全局光照在理论上可以被压缩到仅需 9 个 RGB 系数（共 27 个标量）的紧凑表示，而不会引入可感知的视觉误差。该结论不仅为 PRT 的工程应用扫清了数学障碍，也为所有基于球谐函数的实时 GI 方案提供了理论底线——任何声称使用 SH 进行漫反射 GI 的方法，其合理性都可追溯到该证明。
在 Sloan 最初的 PRT 框架之后，研究者沿多个方向做了扩展。Sloan、Luna 与 Snyder 将 PRT 推广至局部可形变网格[15]，通过对蒙皮动画中的骨骼变换矩阵做 SH 旋转，使预计算的传输系数能够跟随角色姿态变化，将 PRT 的适用场景从静态环境延伸至动态角色。Kavan 等人提出的最小二乘顶点烘焙（Least Squares Vertex Baking）[13] 则从另一个角度切入：将光照计算的结果直接存储在网格顶点而非纹理或探针中，通过最小二乘求解在每个顶点上重建最优的入射辐照度表示，使得光照可以在顶点着色器中高效求值，而无需额外的纹理绑定或查找步骤。该工作的贡献在于打通了"顶点光照"与"预计算求解"之间的联系，为本设计的顶点级重建方案提供了方法论参考。
然而，PRT 路线的实际推广面临两个长期瓶颈。其一，预计算传输矩阵的过程本身计算量可观——对于一个包含数万三角形和数百个探针的场景，在考虑全频率阴影和多次反射时的矩阵维度可能膨胀到难以在普通硬件上求解。其二，也是更关键的，多数 PRT 研究以离线渲染器或自研实验框架为验证平台，缺乏面向 Unity、Unreal 等主流商业引擎的可执行工具链。研究者往往在论文中报告了高质量的离线重建结果，但并未说明这些结果如何导入引擎、如何与现有渲染管线共存、以及在参数异常时如何容错。这种"原型可验证但不可部署"的状态，正是本设计试图打破的局面。
球谐函数拟合方向的近期进展体现在 WishGI[5] 方法中。该方法提出了一个完整的 “离线拟合—运行时重建” 框架：离线阶段通过 K-Medoids 聚类在表面样本空间分布探针，结合半球方向加权最小二乘与岭回归正则化，对每个探针求解二阶 SH 系数；运行时阶段复用网格的 uv2 通道编码顶点-探针关联，在基础渲染通道中完成顶点级的间接光重建。该方法的理论优势在于：二阶 SH 仅需 9 个基函数即可捕捉低频漫反射主成分，配合少量探针（如 128 个）即可在移动端前向渲染管线中达到可用的视觉质量。WishGI 给我们提供了球谐拟合与探针重建的思路参考。
然而，从本设计意图实现的目标来看，现有文献更主要提供的是方法启发，而不能直接替代面向具体引擎环境的系统建设工作。本文立足 Unity URP 的实际开发流程，围绕数据导出、参数校验、结果导入、渲染验证等这些工程问题，并实现了一套完整的离线-运行时工具链。构成本设计主体的，是从场景资产处理、模块接口衔接、异常情况保护到端到端运行验证的一整套系统实现过程。本文的工作重点也落在将低频全局光照方法转化为可部署、可调试、可复现的工程方案上。
1.3 毕业设计主要工作
本毕业设计由离线烘焙管线及 Unity URP 运行时渲染系统组成。离线管线使用 Python 编程语言实现，依次执行四个阶段：表面蓝噪声采样、探针空间聚类与稀疏权重导出、球谐系数拟合以及探针贴图打包。采样阶段采用泊松圆盘策略在三角面上生成蓝噪声分布的样本点[12]，并基于 BVH（Bounding Volume Hierarchy）层次加速结构[1]执行 CPU 路径追踪，记录每个样本在各方向上的辐亮度值。探针分布阶段使用 K-Medoids 算法在样本空间中选取 K 个代表点作为探针位置，同时为每个样本和每个网格顶点分别计算到邻近探针的逆距离加权稀疏权重。拟合阶段将全部样本-方向观测组装为加权最小二乘系统，引入 L2 正则化（岭回归）改善矩阵条件数，为每个探针求解 9 个二阶球谐系数（RGB 三通道共 27 个浮点数）。打包阶段将系数张量重排为一维 RGBAHalf 条带纹理，每探针占用 7 个纹素，128 探针配置下纹理总宽 896 像素，GPU 内存占用仅约 14 KB。
运行时渲染系统基于 Unity URP 前向渲染管线开发，由 C# 导入器脚本和 HLSL 着色器组成。导入器读取离线产出的探针贴图和顶点关联数据，将每个顶点最近两个探针的索引与逆距离权重编码至网格的 uv2 通道，并自动绑定 GI 材质。核心着色逻辑在顶点着色器中完成：从 uv2 解码探针索引与权重，从 ProbeMap 纹理中读取对应探针的 SH 系数并做线性混合，将合成后的 9 个系数传递至片元着色器；片元着色器根据法线方向计算 SH 基函数值并与系数做点积，得到该片元的间接光照颜色。整条管线通过固定随机种子和命令行参数化脚本保证任意机器上的可复现性，运行时纯 GPU 渲染净开销仅为 0.084 ms，适合在算力受限的移动端平台上部署。

2 系统需求分析与总体方案
2.1 项目目标与约束
2.1.1 目标定义
本项目的设计目标可以概括为三条。第一，离线阶段产出的数据格式应当能被运行时直接消费，中间不需要额外的格式转换或人工调整。第二，运行时只依赖 Unity 的基础 URP 渲染通道就能完成 GI 重建，不需要增加后处理或额外的渲染 Pass。第三，采样密度、探针数量、方向数和正则化权重等关键参数都应该暴露给用户，让使用者可以根据场景复杂度和设备预算来调节。
2.1.2 约束条件
项目所受的约束主要来自平台特性和开发周期。平台方面，移动端 GPU 的内存带宽通常在 5~15 GB/s，ALU 算力在 50~200 GFLOPS 之间，跟桌面 GPU 差距很大。这意味着离线烘焙产物的运行时开销必须控制在一张低分辨率纹理的读取量以内，重建逻辑也只能用少数几次纹理采样和简单的代数运算，不能引入额外的渲染通道。
工程方面，毕业设计的时间有限，重点放在把整条链路稳定跑通，暂时不追求覆盖所有功能。数据方面，当前只处理静态网格物体，动态物体的 GI 方案留给后续工作。
2.2 总体架构设计
系统整体分为离线模块和运行时模块两个部分。
离线模块包含四个阶段。采样阶段读取网格数据和场景灯光，生成表面样本点以及每个样本在各方向上的辐亮度。探针分布阶段根据样本的空间分布进行聚类，得到探针位置并导出一组稀疏权重。拟合阶段使用加权线性回归，为每个探针求解球谐系数。打包阶段把系数按 RGBAFloat 格式排布成一维纹理，输出探针贴图及其元数据。
运行时模块包含两部分工作。导入器负责把离线产出的探针贴图和顶点关联数据转写成 Unity 能够识别的资源。Shader 重建阶段根据 uv2 通道中编码的探针索引和权重，在渲染管线中计算最终的间接光照贡献。

2.4 模块接口设计
模块间采用命令行参数加文件输入输出的方式交换数据，每个阶段读取上一阶段的产出文件、处理后再写到下一阶段，中间不依赖任何全局状态。这种设计意味着可以随时中断管线、单独重跑某个阶段，或者在任意一步插入调试代码验证中间结果。
四个阶段的输入输出可以这样概括。采样模块接收网格数据和灯光数据，输出一组表面样本的位置、法线以及每个样本在各方向上的辐亮度，同时可以额外保存一份方向向量文件供后续使用。探针导出模块在样本点上进行聚类，生成探针位置，同时为每个样本和每个网格顶点分别计算到邻近探针的稀疏权重。拟合模块把样本辐亮度、权重矩阵和方向集组装成线性系统，求解每个探针的球谐系数。打包模块把系数矩阵按 RGBA 格式排布成一维纹理，连带元数据一起输出。
为了保证工程上的稳定性，每个模块读到输入数据之后会做几项检查。维度检查确认样本数、方向数、探针数跟预期一致，顶点关联数据里的顶点数和原始网格能对上，拟合出来的系数维度也是正确的。数值检查扫描辐亮度和系数里有没有 NaN 或 Inf，如果在求解矩阵时遇到病态情况就自动切换到备用解法。边界检查处理那些容易出问题的参数组合：探针数比样本数多的时候自动降下来，top-k 参数超过总数的时候截断并给出警告，输出路径是空字符串的时候先创建目录。有了这些检查，管线遇到异常输入时不会无声无息地失败，而是能给出明确的错误信息。

本章详细介绍了本系统的需求分析与总体设计方案，包括项目目标与约束条件、离线端与运行时的模块划分、各阶段之间的数据流与文件规范，以及模块接口设计与工程稳定性检查机制，为后续第三章的核心方法建模和第四章的具体工程实现提供了统一的架构参照。


3 核心方法与数学建模
3.1 球谐光照重建模型
本文使用二阶实数球谐函数（Spherical Harmonics, SH）近似漫反射间接光。根据 Ramamoorthi 与 Hanrahan[1] 的理论分析，漫反射传输函数在频域中是一个仅包含前 3 个频带（L=0,1,2）的极低频信号，可用 9 个 SH 基函数达到 99% 以上的能量覆盖。这构成了本方法使用二阶 SH 的理论依据。
对于任意表面点 p 与观察方向 d ，其重建照明可写为邻近探针球谐系数的线性组合后与 SH 基函数内积：
L(p,d)=k=1Kwk(p)i=19ck,iϕi(d)  ag3.1
其中，K 为点 p 关联的探针数量（本文运行时取 K=2 ），wk(p) 为点 p 对第 k 个探针的插值权重（满足 kwk(p)=1$），$ck,i∈ℝ3 为第 k 个探针的第 i 个 SH 系数（RGB 三通道向量）， ϕi(d) 为方向 d 上的第 i 个实 SH 基函数。
本文采用的二阶 SH 基函数在实现中已预先与漫反射余弦核（cosine lobe）做卷积[1]，从而将渲染方程中的半球积分转换为基函数与系数的点积。9 个基函数从 L=0 至 L=2 依次排列如下（方向 d=(x,y,z) 为单位向量）：
ϕ1(d)=c0
ϕ2(d)=c1y, ϕ3(d)=c1z, ϕ4(d)=c1x (L=1三基函数)
ϕ5(d)=c2xy, ϕ6(d)=c2yz, ϕ7(d)=c3(3z2−1)
ϕ8(d)=c2xz, ϕ9(d)=c4(x2−y2) (L=2五基函数)
其中，卷积常数 c0≈0.28209 c1≈0.32574 c2≈0.27314 c3≈0.07885 c4≈0.13657 ，与 Ramamoorthi 的解析推导[1]一致。这些常数在离线 Python 端（sh_basis.py）与运行时 HLSL 端（WishGIProbe.hlsl）必须保持完全一致，这是保证离线拟合与运行时重建数值一致性的关键约束。公式(3.1)本身则体现了分治思想：探针权重 wk(p) 表示空间变化，SH 基函数集 {ϕi(d)} 表达方向变化，二者的乘积与叠加即可重建任意观测方向上的间接光照。
3.2 采样与方向权重建模
以下是方向采样所采用的策略。对每个表面采样点 p ，以法线 np 为上半球方向集 Ω$（$|Ω|=D ，本文取 D=256 进行辐亮度观测。方向集采用斐波那契球面螺旋均匀分布在单位球面上，仅保留与法线夹角小于 90° 的方向（即 d⋅np>0 ），形成半球方向集。采样阶段对每个有效方向执行路径追踪，记录辐亮度值 L(p,d) 。
然后是方向权重的设计。考虑到漫反射贡献按余弦分布集中于法线邻域，引入方向权重函数。该权重在法线方向取值最大（ w=1 ），在切平面处衰减至零，与 Lambert 漫反射余弦项一致：
w(d,n)=max(0,d⋅n)  ag3.2
接下来定义拟合过程的损失函数。损失函数衡量的是重建光照与参考光照之间的整体偏差，将全部采样点 S 与全部有效方向 Ω 的观测值汇总，以方向权重 w(d,np) 对各观测项的贡献进行差异化加权，构建如下加权最小二乘目标：
Elight=p∈Sd∈Ωw(d,np)L(p,d)−L(p,d)2  ag3.3
其中， S 为表面采样点集， L(p,d) 由式(3.1)给出， L(p,d) 为路径追踪得到的参考辐亮度。式(3.3)中的方向权重 w(d,np) 使拟合过程更加关注几何法线邻域——法线方向的偏差被赋予更高权重，偏离法线的方向虽被采样用于覆盖方向分布，但在损失中的贡献被余弦权重压低，从而在同等方向数下提高视觉有效信息利用率。
在工程实现中，该加权通过将方向权重 w 乘入设计矩阵的对应行来完成，等效于对每组样本-方向观测施加异方差加权。拟合阶段的 fit_sh.py 在构建设计矩阵 A 和目标向量 b 时同步执行该加权，无需后处理。
3.3 探针分布与权重估计
3.3.1 K-Medoids 探针分布
设采样点集合为 S={pi} ，共 N 个样本点，每个样本点 pi 具有三维空间坐标。目标是找
到 K 个代表点（medoids） {o1,o2,…,oK} ，其中 oj∈S ，最小化各样本到其最近 medoid 的欧几里得距离之和：
Ecluster=j=1Kp∈Cj‖p−oj‖2  ag3.4
其中 Cj 为归入第 j 个 medoid 的样本簇，满足 jCj=S 且 Ci∩Cj=∅$（$i≠j 。
本文选用 K-Medoids 而非更常见的 K-Means，主要基于三方面考虑。首先，K-Medoids 的聚类中心必须是真实样本点，而 K-Means 的簇中心是样本均值，可能落在几何体外部或空区域中。对于分布在物体表面的采样点来说，落在三角面上的代表点更适合作为探针的放置位置。其次，K-Medoids 最小化的是绝对距离和，而 K-Means 最小化平方距离和，前者对离群样本点更不敏感。最后，每个探针都可以追溯到具体的表面采样位置，这给后续的调试和可视化带来了便利。
算法通过 PAM（Partitioning Around Medoids）迭代实现：初始化阶段以最远优先策略选取 K 个初始 medoids，随后交替执行分配步骤（将每个样本分配给最近 medoid）与更新步骤（在簇内逐一尝试替换 medoid 以降低  ），直至收敛或达到最大迭代次数（30 次）。

3.4 SH 拟合与正则化求解
将 3.2 节的加权损失函数与 3.3 节的探针体系结合，问题转化为：给定 Ns 个样本点、 D 个方向、 Kp 个探针，为每个探针求解 C=9 个 SH 系数的 RGB 三维向量，使式(3.3)最小化。
以下为设计矩阵的构建。将所有样本-方向观测展开为线性系统。每个样本点 P 关联 Ktop 个探针（本文离线取 Ktop=4 ，运行时取 Ktop=2 ），每个有效方向 d （满足 d⋅np>0 ）生成一行观测。设计矩阵 A∈ℝM×(Kp⋅C) 的每一行包含非零列和零列：样本关联的 Ktop 个探针对应的 C 列位置填入 w(d,np)⋅wp,k⋅ϕi(d) ，其余列填零。目标向量 b∈ℝM 的对应行则填入 w(d,np)⋅L(p,d) ，其中 w 乘子是方向加权在矩阵形式下的等价格式，确保正规方程精度为正。
若所有样本-方向对均有效，应有 M=Ns×D=1024×256≈2.62×105 行。但由于方向为半球筛选（ (d⋅np>0) ），约一半方向被裁剪，且部分样本的可见方向进一步受几何遮挡影响，实际构建的 A 行数约为 13 万（如第 5 章实验日志所示）。每个探针的 9 个 SH 系数按 RGB 三通道独立展开，故 A 的列数为 Kp⋅C=128×9=1152 。这是一个典型的"高瘦"形状（M≫ 列数），适合通过正规方程 ATA 降维后求解。
此外未经正则化的普通最小二乘解 $\min_x \|Ax-b\|_2^2$ 在 $A^T A$ 近奇异或存在共线性时会产生数值不稳定（表现为某些 SH 系数异常大，运行时出现偏色或亮度闪烁）。为此引入 L2 正则化（Tikhonov 正则化 / 岭回归），其目标函数和正规方程分别为：
minx ‖Ax−b‖22+λ‖x‖22  ag3.6
(ATA+λI)x=ATb  ag3.7
其中 λ 为正则化强度， I 为单位矩阵。正则化项 λ‖x‖22 约束系数幅值，等价于在 ATA 的对角线上添加正值 λ，改善矩阵条件数。
本文使用 λ=0.1 ，该值的选取通过经验调参确定： λ 过小（<0.01）时正则化效果不足，病理探针仍会出现系数异常； λ 过大（>1.0）时过度抑制系数幅值，导致拟合结果过暗。 λ=0.1 在实验中取得了稳定性与拟合精度的平衡。
当 ATA+λI 由于数值原因仍无法通过标准 Cholesky 分解求解（numpy 抛出 "LinAlgError"）时，系统回退至 numpy.linalg.lstsq 计算最小二乘解。该方法底层采用更稳定的矩阵分解策略，可在矩阵接近奇异时降低数值误差放大的风险。
3.5 运行时重建与复杂度分析
运行时重建在 Unity URP 的基础渲染通道（Base Pass）中完成，分为顶点着色器阶段和片元着色器阶段。
顶点阶段的作用是进行索引解码与系数混合：每个网格顶点在离线阶段已通过 mesh_assoc.json 获得了两个最近探针的索引与逆距离权重，编码存储于 uv2 通道。在顶点着色器中，从 uv2 解码两个探针索引 (i0,i1) 与对应权重 (α,β) （ i0,i1 为经 round(uv2.x * (probeCount-1)) 恢复的整数索引， α,β 为归一化后的插值权重且 α+β=1 ）。随后从 ProbeMap 纹理中读取探针 i0 和 i1 各自的 9 个 SH 系数（每探针 27 个浮点数，封装于 7 个 RGBA 纹素），按权重做线性混合，得到该顶点的 9 个合成 SH 系数：
ci(v)=α⋅ci0,i+β⋅ci1,i, i=1,…,9  ag3.8
混合后的系数通过顶点输出传递给片元着色器，供后续的 SH 基函数求值与间接光照计算使用。
片元阶段的作用是针对法线方向进行求值。片元着色器接收插值后的法线（世界空间），调用 EvalSH9_L2(dir) 计算 9 个 SH 基函数在该方向上的值，然后与顶点传递的合成 SH 系数做点积得到该片元的间接光照颜色。最终与材质的 BaseColor / Albedo 做逐分量乘法调制，叠加在直接光照之上完成 GI 渲染。
下面是对复杂度的分析。二阶 SH 下，每个探针存储 27 个浮点数（9 个系数 × 3 通道），封装为 7 个 RGBA 纹素（ 7×4=28 个分量，27 个有效 + 1 个冗余）。128 个探针的总纹理宽度为 128×7=896 ，纹理尺寸为 1×896×4 float，占用 896×4×4=14.34 KB GPU 内存。顶点着色器每个顶点执行一次双探针系数读取（14 次纹理采样）与混合（18 次乘法 + 9 次加法），片元着色器每个片元执行一次 SH 基函数求值与点积（9 次乘法 + 8 次加法）。此复杂度在移动端 GPU（50~200 GFLOPS ALU，5~15 GB/s 带宽）上属于极低开销级别。

4 系统实现
4.1 离线采样模块实现
采样模块（Offline/sampling/sample_surface.py，约 800 行）是离线管线的第一步和计算耗时最高的环节。输入为 mesh JSON（由 Unity MeshBakeExporter 导出，包含顶点、三角形、材质反射率、UV0 和纹理引用）与 scene lights JSON（由 SceneLightExporter 导出，包含灯光位置、颜色、强度和环境光），输出为包含样本位置、法线和每方向辐亮度的 JSON 文件，以及方向集 NPY 文件供后续拟合复用。
图4.1 采样模块流程图

数据结构上采用了BVH树加速结构。为支持对复杂场景的高效可见性查询，系统对全部三角面构建层次包围盒（Bounding Volume Hierarchy, BVH）。构建采用自顶向下的递归分割策略：在每个节点上，沿包围盒的最长轴以中位数切分三角面，左子树包含中位数左侧的三角形，右子树包含右侧的三角形；当节点内三角形数目 ≤4 时停止递归，形成叶节点。光线-三角形求交采用 Moller-Trumbore 算法，通过单一线性方程组判断光线在三角形内的交点参数 (t,u,v) ，单次求交仅需约 20 次标量乘加运算。
表面采样使用了蓝噪声算法[12]生成采样点。采样模块使用泊松圆盘（Poisson Disk）采样策略在三角面上生成蓝噪声分布样本点。通过按面累积面积构建 CDF，以蒙特卡洛重要性采样方式选择三角面；面内采样使用均匀随机重心坐标。蓝噪声通过空间哈希网格施加最小距离约束（min_dist 参数，默认为 0.05 场景单位）：每个候选点若与已有样本的欧几里得距离小于阈值则被拒绝。网格单元边长设为 min_dist/3 ，确保每个单元内的候选点自动满足距离约束。采样以 50× 目标数量的上限防止死循环。

对每个采样点在各预设方向上执行自定义 CPU 路径追踪器，估计辐亮度值。其值为直接光照加上间接光照。
直接光照的计算方法。对每条从采样点出发的方向光线，在 BVH 中查询首次命中。如命中三角面，采用重心坐标插值 UV，在材质纹理上做双线性采样并经 sRGB→线性转换获得表面反射率（sample_albedo 函数）。在命中点查询所有光源的直接光照贡献。
间接光照的计算最多经过三次反弹。在命中点以余弦加权半球采样生成新的漫反射方向（sample_cosine_hemisphere），递归执行下一次路径追踪。第三次反弹起启用俄罗斯轮盘赌（存活概率 0.9），以无偏方式终止低贡献光路。
当光线逃逸出场景（BVH 无命中）时记录环境光（若场景包含环境光）。否则达到最大反弹次数后停止。
此模块的输出格式如下。每个样本输出一个 JSON 条目，包含位置（position.{x,y,z}）、世界空间法线（normal.{x,y,z}）、所属三角面索引与重心坐标供纹理反射率采样、以及一个 radiancePerDir 数组，长度为方向数 D，每个元素为 RGB 三通道辐亮度值。同时可选输出方向集 NPY（形状 (D, 3)），供拟合阶段复用同一方向集。采样阶段通过固定随机种子（--seed 42）和确定性哈希算法保证结果在任意机器上可复现。

探针聚类。使用第 3.3.1 节所述的 K-Medoids 算法，在样本点位置空间中找到 K 个 medoids 作为探针位置。核心参数包括探针数量 K 样本关联探针数 top_k_sample（用于拟合阶段的权重矩阵 W ）和顶点关联探针数 top_k_vertex（用于运行时 uv2 编码）。算法输出探针列表 JSON（含探针序号、世界空间位置）、样本-探针稀疏权重矩阵 JSON、以及顶点-探针关联 JSON。

4.3 SH 拟合与打包模块实现
SH 拟合模块（Offline/baking/fit_sh.py，约 230 行，配合 loss.py 的岭回归求解器与 sh_basis.py 的基函数计算）：读取采样样本、样本-探针权重矩阵和方向集 NPY，逐探针构建设计矩阵 A 和目标向量 b （按第 3.4 节所述方法），调用岭回归求解器输出 Kp×9×3 的 SH 系数张量（probes_sh.npy）。
为保证离线拟合与运行时重建的严格一致性，本模块中的 SH 基函数实现（sh_basis.py）与运行时 HLSL 代码（WishGIProbe.hlsl）使用完全相同的 5 个漫反射卷积常数：
c0=0.28209479177387814c1=0.32573500793527993c2=0.2731371076480198c3=0.07884789131313001c4=0.1365685538240099
这些常数源自 Ramamoorthi[1] 的解析求导结果，乘以二阶 SH 基函数的原始形式后得到最终使用的 9 个基函数（排列顺序见第 3.1 节）。一致性约束在日常开发中也便于独立调试——若修改基函数常数，必须同时在 Python 端和 HLSL 端更新，否则会出现偏色。
其中 ProbeMap 为打包模块（Offline/baking/pack_probes.py，约 130 行）：将拟合产物的 (P, 9, 3) 三维系数张量重排为 Unity 可读取的 RGBAFloat 一维纹理条带。打包流程如下。将拟合产物的 (P, 9, 3) 三维系数张量重排为 Unity 可读取的 RGBAFloat 一维纹理条带。打包时先把系数展平为一维浮点序列，长度是 P×27 。然后按 RGBA 四个通道分段，每 4 个浮点数打包为 1 个纹素，共需要 ⌈P×27/4⌉=P×7 个纹素——最后一个纹素的 A 通道会多出一个冗余分量。最终写入形状为 (1, width, 4) 的 NPY 文件， width=P×7 。P=128 时 width 为 896。同时输出的元数据 JSON 记录了 texels_per_probe 和 num_probes 等信息，供 Unity 导入器设置着色器参数。为防止输出路径仅为文件名而无父目录的边界情况，打包脚本在写文件前显式创建输出目录。

4.4 Unity 导入与运行时 Shader 实现
Unity 侧实现分为 Editor 工具链（C#）和运行时 Shader（HLSL）两部分，共同完成从离线数据到屏幕渲染的闭环。
Unity Editor 脚本（WishGIBakingTool.cs，约 1000 行）实现ProbeMap 纹理导入和网格关联写入。首先该脚本从 Python 管线的输出目录读取 probe_map.npy 和 probe_map_meta.json，创建 Texture2D 资产并设置关键导入参数。纹理格式采用 RGBAFloat，并且使用 16-bit float 而非 32-bit，这能节省约一半的 GPU 内存——128 探针下从大约 28 KB 降到约 14 KB——同时仍然满足 SH 系数的动态范围要求。滤波模式设为 Point，因为 SH 系数在探针条带上是逐个探针紧密排列的，线性插值会导致相邻探针的系数相互渗色。包裹模式设为 Clamp，因为这张纹理本质上是一维条带，UV 坐标不应越界。sRGB 选项必须关闭，因为 SH 系数是线性空间的浮点数据，如果被 gamma 校正会直接破坏数值，造成亮度偏差。
然后该脚本会进行网格关联写入。导入器读取 mesh_assoc.json，对每个网格的每个顶点，将其最近两个探针的索引和权重编码到 uv2 通道。编码方式为：
uv2=(i0probeCount−1, w0, i1probeCount−1, w1)
其中索引归一化到 [0, 1] 范围，运行时通过 round(uv2.x * (probeCount-1)) 恢复整数索引。网格通过 Unity 的 Mesh.SetUVs(1, ...) API 写入 uv2，并自动分配 WishGI 材质。
而后是运行时 Shader 实现。核心计算集中在两个 HLSL 文件中。WishGIProbe.hlsl（约 80 行）提供了三个核心函数：EvalSH9_L2 以世界空间法线方向为输入，计算 9 个经过漫反射卷积的 SH 基函数值；FetchProbeCoeffs 从 ProbeMap 纹理中按探针索引定位 7 个纹素，解码出 27 个浮点数的 SH 系数；SampleWishGI 从 uv2 解码出双探针的索引和权重，分别评估每个探针对法线方向的 GI 贡献，再按权重混合得到最终的 GI 颜色。WishGIUnlit.shader （约 90 行）是一个基于 Unity 通用渲染管线（URP）[14] 定制的 Unlit Shader ，在顶点着色器中调用 SampleWishGI 获得 GI 贡献并传递到片元着色器，片元着色器再将其与材质的 BaseColor 或 Albedo 做逐分量乘法调制：最终颜色等于 GI 乘以 BaseColor 乘以 GI 强度乘以色调微调。

4.5 工程健壮性修复与调试记录
围绕"系统可跑通"的目标，本文对几类关键问题进行了修复。第一是 SH 基函数在离线端和运行时不统一的问题，两者使用的常数不一致会导致画面偏色和亮度偏差，修复后两端的数值完全对齐。第二是矩阵求解时的奇异问题，当正规方程接近奇异时求解器会抛出异常，程序现在会自动回退到最小二乘法来避免中断。第三是 top-k 参数的边界情况，用户传入的值可能超过实际可用的探针数，需要做截断保护。第四是输出路径的处理，有些脚本接收到的路径只有文件名而没有父目录，现在会在写文件前自动创建目录。第五是默认参数的不一致问题，不同脚本对正则化权重的默认值定义不同，现在统一为 0.1。

5.4.2 运行时性能测量
为评估系统在轻量化部署环境下的优势，本文采用剔除扰动的差值对比法来测量真实净开销。测试过程关闭引擎帧率限制与垂直同步以暴露真正的硬件耗时极限。在关闭全局光照重建与开启全局光照这两个状态下，连续采集多帧的硬件级计时数据并求取平均值。这两种状态的开销差值，即代表整个方法由于在顶点阶段做 SH 插值、UV 解码等计算产生的纯硬件负担。此作差测量法直接提取实际管线数据，排除了复杂的外部系统干扰，可精确量化性能的可用性。

5.5 消融与误差来源分析
为更清晰地理解各环节对最终效果的影响，本文从工程角度做了误差来源分析。采样点密度不足会导致局部光照不稳定，方向数太低时拟合偏差会增大，探针数过少则跨区域的光照变化无法被充分表达。正则化参数的选择也很关键，太小就起不到稳定作用，太大会让拟合结果偏暗。此外，离线端和运行时的基函数常数如果不一致，会产生系统性的偏色。

从误差传播的路径来看，采样阶段的随机性经路径追踪传递至辐亮度观测值，再通过最小二乘拟合映射到 SH 系数上，最终在着色器中重建为像素颜色。每一个环节的误差都会沿数据流向下累积，因此本文的策略是优先保证一致性和稳定性，再逐步提高质量参数——即"先跑通、再优化"。具体而言，常数对齐和求解器容错属于必须优先解决的阻断性问题，而采样密度和方向数则可在管线稳定后按需调优。

6 结论与展望
6.1 工作总结
本文围绕静态全局光照的轻量化实现，完成了从离线算法到 Unity 运行时的完整链路建设。具体来说，构建了一套涵盖 Python 离线四阶段和 Unity URP 运行时的统一工具链，实现了从一键烘焙到场景渲染的闭环。工程方面修复了影响系统稳定性的五个关键问题，使系统在非常规输入下仍然能够保持可执行状态。在 128 探针、二阶 SH、256 半球方向、1024 个采样点的配置下完成了端到端的验证，各阶段输出维度正确，没有出现数值异常。通过固定随机种子、统一数据格式和命令行参数化脚本，确保了论文的工作可以在不同机器上复现。将论文方法从概念正确推进到工程可用，这过程中记录的问题发现和修复过程构成了本文的主要价值。
6.2 不足分析
当前方案仍有几处不足。动态物体的全局光照还没有纳入支持，目前只适用于静态场景。二阶球谐函数在频域上对高频信息做了截断，细节丰富的阴影边界会显得模糊。多个网格各自独立的探针生成还没有实现自动化批处理，需要手动处理。评价指标方面，目前主要依赖工程可执行检查和维度一致性验证，还缺少主观图像和客观指标之间的定量对照。
6.3 后续研究方向
后续可以从四个方向继续推进。一是实现多网格的独立探针贴图自动输出和资源管理。二是把可见性图和测地距离引入探针分布环节，减少漏光问题。三是支持多时段探针贴图的插值，用极低的代价实现昼夜光照过渡。四是增加与光照贴图、体积探针等方案的对比实验，并使用客观指标做更系统的定量评估。
